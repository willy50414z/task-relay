## Arbiter Summaries
- `claude_plan_ceo_review`: The change targets a real and valuable product problem: proving context-packer actually reduces token cost without degrading downstream quality, and closing the gap between the model-fallback contract and real packet assembly. Scope is correctly bounded (deterministic-first, no new vector DB, three-layer benchmark). However, two product-critical decisions are still open inside the artifacts (budget configuration surface and sidecar format), and one new capability lacks a verifiable spec requirement (concrete quality-proxy schema). These must be resolved before implementation so acceptance is testable. The frozen-dataclass and extra_reads/integration concerns are valid but are implementation-detail risks better owned by eng review, not blocking from a product/scope standpoint.
  - `design.md`: Resolve the budget configuration decision: state where the packet budget limit originates (e.g. a budget_bytes sidecar field and/or a --packet-budget flag on `trly pack`), the default value, and whether the limit is hard (enforced trimming) or soft (report-only). Remove this from Open Questions and reflect it in tasks 2.1-2.4 scope. (acceptance: design.md names a single concrete configuration source, a default, and hard-vs-soft semantics; specs/context-packer-budgeting/spec.md is consistent with that decision and no longer references an undefined 'configured budget' without origin.)
  - `specs/context-packer-benchmarking/spec.md`: Add a requirement defining the concrete machine-readable downstream quality-proxy field schema (e.g. review_artifact_sections_present, apply_exit_code/verification_passed, retry_count) so the 'quality outcome' benchmark layer is verifiable. Task 3.3 currently has no spec requirement covering the actual field names. (acceptance: spec.md enumerates the named quality-proxy fields with present/missing semantics, and task 3.3 can be checked complete by asserting those exact fields appear (or are explicitly marked missing) in the benchmark report.)
  - `design.md`: Close the sidecar-format open question by committing to one contract. Adopt the design's own JSON-only recommendation: specify that .yml/.yaml files are parsed as JSON and that non-JSON content is rejected with a clear lint/error message (not silently ignored). Update tasks.md 4.1 from a decision point to an implementation task. (acceptance: design.md states the single chosen format contract, specs/lint behavior for .yml/.yaml is defined, and tasks.md 4.1 no longer presents the choice as unresolved.)
  - `specs/context-packer-semantic-assembly/spec.md`: Add a scenario clarifying the interaction between CLI-supplied extra_reads and model-fallback-proposed extra_reads (additive vs override) and how each is treated during budget trimming, so the dual-source behavior is specified rather than left ambiguous. (acceptance: spec.md contains a scenario covering combined CLI + model extra_reads with defined merge/precedence and trimming order; the budgeting trim order in specs/context-packer-budgeting/spec.md remains consistent with it.)
- `claude_plan_eng_review`: From an engineering-feasibility standpoint the change is sound and correctly bounded (deterministic-first pipeline, no new vector DB, bytes-with-optional-trace benchmark). However several implementation-critical decisions are still unresolved in the artifacts and block a clean, testable build: (1) the PacketPlan construction/mutation pattern under new budget fields, (2) the budget origin AND its measurement unit (bytes vs token estimate) which the design currently mixes, (3) whether actual token/cost is read from delegate trace or estimated-first, and (4) the lack of a trimmed-packet integrity test. The prior CEO arbiter explicitly deferred the frozen-dataclass blast radius and the trimmed-packet integration test to eng-review; this arbitration promotes both to binding. The quality-proxy schema and sidecar-format items are already bound by the CEO arbiter and are not re-litigated here.
  - `design.md`: Decide and document the PacketPlan construction pattern under the new budget fields (budget_status, trimmed_sections, budget_limit). State explicitly whether PacketPlan stays frozen (new fields populated at construction by plan_packet, with build_packet/to_report only reading them) or becomes a two-phase build (immutable selection result + a separate budget/trim result), and enumerate the call sites that change. Trimming must happen in a defined stage rather than mutating a frozen instance ad hoc. (acceptance: design.md names the chosen pattern, lists the affected functions (plan_packet, build_packet, to_report and any constructors), and confirms no construction site is left passing a stale signature; tasks 2.1-2.3 reference this pattern as their structural basis.)
  - `design.md`: Resolve the budget measurement unit and origin together. The design currently references both byte_estimate and 'token estimate' for the same budget; pick the unit the trim loop actually enforces (bytes, or a single defined token-estimate function) and name the single configuration source (e.g. budget_bytes sidecar field and/or --packet-budget flag), its default, and hard-vs-soft semantics. Ensure specs/context-packer-budgeting/spec.md uses that same unit for 'configured budget'. (acceptance: design.md and specs/context-packer-budgeting/spec.md agree on one budget unit and one configuration origin with a stated default and hard/soft behavior; no artifact references an undefined 'configured budget' or mixes bytes and tokens for the same threshold.)
  - `design.md`: Close the Open Question on actual token/cost sourcing by committing to an estimate-first contract with optional trace enrichment: define the deterministic estimation used when no trace exists and where trace usage is read from when available, so benchmark (tasks 3.1-3.2) is implementable without requiring live delegate integration. Remove this from Open Questions.
